# cloud-agent-infra

A cloud-hosted, always-on **Debian agent box**: a small Google Compute
Engine VM running Debian 12, reached over Tailscale from your laptop or phone.
Long-running agents (via tmux, or `opencode serve`) keep working while your local
machine is asleep.

Infrastructure is defined as code (Terraform), with a single source of truth
for configuration shared between the bootstrap script and Terraform.

**This file is the operator's manual — what the machine is and how to drive it.**
The rest of the documentation is deliberately elsewhere, one answer per question:

| Question | Where |
|---|---|
| What is this for, what exists, what is undecided | `SPEC.md` |
| What is still to be done | `TASK.md` |
| **Why** something is the way it is | [`docs/decisions/`](docs/decisions/) |
| The numbers behind those decisions | [`docs/measurements.md`](docs/measurements.md) |

## Architecture

```
┌─────────────────────────────────────────────────────────────┐
│  GCE VM  "cloud-agent"   (Debian 12, me-west1)              │
│                                                             │
│   • Debian stable + apt; unattended security updates        │
│   • tailscaled (systemd) -> joins tailnet as "cloud-agent"  │
│   • Tailscale SSH: `ssh <user>@cloud-agent` lands here      │
│   • opencode (pinned) + Node 24 — the agent runner          │
│   • Xvfb :99 + two Chromium wrappers:                       │
│       headed-chromium  CDP, for testing our own apps        │
│       social-chromium  no CDP ever, for logged-in accounts  │
│   • x11vnc, loopback only, started by hand for a login      │
│   • Persistent data disk mounted at /mnt/data               │
│     (writable root — no COS quirks)                         │
└─────────────────────────────────────────────────────────────┘
          ▲
          │  Tailscale (private tailnet, no public inbound)
          ▼
   Laptop / phone:  ssh <user>@cloud-agent
```

## Prerequisites

- A Google Cloud project with **billing enabled**.
- `gcloud` and `terraform` installed locally. (No `direnv` — see below.)
- A [Tailscale](https://tailscale.com) account and a tailnet **API key** (admin
  console → Settings → Keys). The tooling mints its own single-use auth key per
  build from that; you do not manage auth keys by hand.
- Application-default credentials for Terraform:
  ```sh
  gcloud auth application-default login
  ```

## Configuration: single source of truth

All shared config lives in **`config.env`**. Terraform reads any `TF_VAR_*`
environment variable natively, and the shell scripts source the same file —
one place to edit.

```sh
cp example.config.env config.env
```

```sh
# config.env  (git-ignored — contains a secret)
TF_VAR_project_id="your-project-id"
TF_VAR_region="me-west1"           # Tel Aviv: lowest latency from Israel
TF_VAR_zone="me-west1-a"
TF_VAR_machine_type="e2-standard-2"  # 2 full vCPU/8GB for agents+browsers; e2-medium is leaner
TF_VAR_instance_name="cloud-agent"   # also the tailnet hostname
TF_VAR_ssh_user="youruser"           # your Unix user on the box
TF_VAR_data_disk_size_gb="20"        # persistent disk for repos + tailscale state (optional, defaults to 20)
TF_VAR_termux_host="galaxy-s24-ultra" # phone's Tailscale MagicDNS name, for notify-phone (optional)
TF_VAR_termux_ssh_user="u0_a221"      # `whoami` inside Termux, required for notify-phone to work

# Tailnet admin key. bootstrap.sh mints a single-use auth key per build from it,
# and cleanup.sh deletes the stale node. See example.config.env for the details.
TAILSCALE_API_KEY="tskey-api-..."
```

`TF_VAR_data_disk_size_gb` is optional — omit it to use the default (20 GB).

> Do **not** also set `TF_VAR_tailscale_auth_key`. Terraform ranks
> `terraform/tailscale.auto.tfvars` (written by `mint`) above `TF_VAR_*` env vars,
> so a key here is ignored on every normal build and then silently takes effect —
> as a long-spent key — if that file ever goes missing. Set one or the other.

> `TF_VAR_ssh_public_key` is **optional** and usually unnecessary — it
> authorizes your own key for sshd, but `gcloud compute ssh
> --tunnel-through-iap` injects an ephemeral key of its own, and Tailscale SSH
> needs no key at all. Set it only if you connect to sshd through a raw IAP
> tunnel with your own key (e.g. editor Remote-SSH without Tailscale).

No `export` prefixes, and **nothing to source or activate**. Every entry point
calls `load_config` (`scripts/lib.sh`), which wraps the `source` in `set -a` so
`TF_VAR_*` land in the environment where `terraform` can see them. `./run` works
in a completely bare shell:

```sh
env -i HOME="$HOME" PATH="$PATH" ./run plan   # No changes.
```

> **Why no direnv?** An `.envrc` with `dotenv config.env` used to live here and
> actively caused a bug, and it leaked the tailnet-admin `TAILSCALE_API_KEY` into
> every process started from this directory — agents included. Config loading now
> has exactly one definition. Full reasoning:
> [`docs/decisions/infrastructure.md`](docs/decisions/infrastructure.md).

## The one command

```sh
./run up
```

That is it. `up` is a **convergence** command, not a build script: every step
first asks what is already true and does nothing if the answer is "already
correct". So it is the command to run when the box is broken, when it is
half-built, when it is fine, and when you don't know which. It ends by running
`verify.sh`, so it can't lie to you about the result.

It is **non-destructive by contract.** It will reboot the VM when that is the
only way to deliver an auth key, but it never destroys or deletes anything — not
the VM, not the data disk, not the state bucket, not a tailnet node. It cannot
cost you the notify keypair, your browser logins, or the work on `/mnt/data`.

What it converges, in dependency order, doing only what is missing:

| # | Converges | Acts only if |
|---|-----------|--------------|
| 1 | Terraform state backend | `backend.tf` or the backend record is absent |
| 2 | Tailscale auth key | the current key is unusable (spent, revoked, missing) |
| 3 | Infrastructure | `terraform apply` — always; it is itself a converge |
| 4 | Guest has consumed the key | the VM is not online in the tailnet |
| 5 | Local `known_hosts` | a stale entry from a previous VM is blocking SSH |
| 6 | Phone notify key | always (idempotent; the most drift-prone fact there is) |
| 7 | Proof | `verify.sh`, non-zero exit on any drift |

Step 4 is the one that does not follow from `apply`, and the reason `up` exists —
see [`apply` cannot re-key a running VM](#apply-cannot-re-key-a-running-vm).

Every step is still individually runnable (`./run verify`, `./run phone`,
`./run rekey`, …); `up` only encodes the order and the conditions so they can't be
got wrong by hand. `./run` with no arguments lists everything.

### Rebuilding from scratch

`./run rebuild` is the destructive sibling: it starts with `cleanup.sh`, so it
**destroys the data disk, the state bucket and the tailnet node** before
rebuilding. That means a new notify keypair, a stale pinned key on the phone, and
the loss of everything on `/mnt/data`. Reach for it only when you mean exactly
that — `up` is what you want the other 99% of the time.

```sh
./scripts/cleanup.sh          # tear down + delete the tailnet node
./scripts/bootstrap.sh        # state bucket + backend.tf + init + mint a one-off auth key
./run apply                   # instance created; reachable ~40-60s later
./scripts/wait-ready.sh       # block until on the tailnet AND startup script done
./scripts/provision-phone.sh  # re-key the phone to the VM's CURRENT pubkey
./scripts/verify.sh           # assert the entire end state, non-zero on any drift
```

`up` from nothing at all reaches the same end state without the destruction: it
bootstraps, mints, applies, waits for first boot, re-keys the phone, and verifies.

`run` is a dispatcher, not a Makefile: it sources `scripts/lib.sh`, so config
loading and the terraform wrapper have a single definition, and arguments pass
straight through (`./run verify --quick`, `./run tf state list`).

No admin-console step: with `TAILSCALE_API_KEY` set, `bootstrap.sh` mints a
fresh **single-use, pre-approved** auth key per build (into the git-ignored
`tailscale.auto.tfvars`, which Terraform auto-loads), and `cleanup.sh` deletes
the stale node — including any `cloud-agent-N` duplicate — so the next build
always gets the clean MagicDNS name. Nothing long-lived is left in `config.env`
except the API key itself.

> **Never delete a node whose VM you intend to keep.** tailscaled stores its node
> identity on the data disk, so once the node is gone server-side every netmap
> poll fails with `404: node not found` and the box is unreachable — it cannot
> rejoin without a fresh key. `cleanup.sh` only deletes the node after `gcloud`
> confirms the instance is gone. To recover an orphaned VM: `./run rekey`.

### The boot is two phases, and the split is the point

`startup.tf` runs in two phases:

**Phase A (foreground, ~40-60s)** does only what is needed to *reach* the box:
mount the data disk, install Tailscale, create your user, `tailscale up`. The
single-use auth key is spent at the end of phase A.

**Phase B (background, ~4 min)** is everything else, in waves: the CLI tools
(`git`, `stow`, `tmux`, `vim`), `apt upgrade`, the headed-browser stack (chromium,
fonts, Xvfb, xauth, x11vnc, `libgl1-mesa-dri`, zram), Node.js 24 from the vendor
apt repo, and **opencode at a pinned version** as a single root-owned binary in
`/usr/local/bin`. It runs as `agent-packages.service`, launched with
`systemctl restart --no-block`, so the metadata script runner returns immediately.

This ordering was measured, not guessed:

| | before (single phase) | after (two phases) |
|---|---|---|
| instance created → auth key consumed | **4m34s** (274s) | **1m24s** (84s) |
| of which: GCE guest boot before the script runs | ~41s | ~41s |
| of which: the startup script itself | ~233s | **43s** |

Chromium's codec dependencies are ~200MB and have nothing to do with
reachability — but until `tailscale up` runs the VM has no public inbound, so it
is unreachable *and* undebuggable, and a bad auth key takes five minutes to even
surface. Phase A is now ~43s of actual work; the remaining 41s is GCE booting the
guest before it hands over, which this repo does not control.

```sh
./run ssh journalctl -u agent-packages -f   # watch phase B
./run ssh systemctl is-active agent-packages # activating | active | failed
./run wait --packages                        # block until phase B finishes
./run verify-browser                         # assert the browser stack alone
```

Phase B is an enabled oneshot unit, so it re-runs on every boot and is a no-op
when the packages are current — which also means it self-heals a failed install.

Because the box is deliberately declared ready before phase B finishes,
`verify.sh` reports the browser checks as **SKIP** while `agent-packages` is
`activating`. That is not drift; those facts are not answerable yet. `./run up`
tells you when it happens and how to finish the assertion.

### The browser check is a sidecar

`verify-browser.sh` is separate from `verify.sh` for two reasons: it is the only
*slow* check (it launches a real Chromium and waits for CDP), and it is the only
one that depends on phase B. `verify.sh` starts it as a **sidecar** — a
concurrent job launched before the main fact gathering and joined at the end — so
its Chromium launch overlaps with everything else instead of adding to the wall
time. Its verdicts are spliced into the single `Result:` tally, so there is still
one exit code.

It also stands alone, which is what you want when phase B was still installing
during `up`:

```sh
./run verify-browser            # full, human-readable
./run verify-browser --quick    # skip the Chromium/CDP launch
```

### `apply` cannot re-key a running VM

The auth key reaches the VM through the `startup-script` **metadata** value, and
GCE only runs `startup-script` at **boot**. So minting a key and applying against
an instance that already exists is a metadata-only update:

```
Plan: 0 to add, 1 to change, 0 to destroy.
Apply complete! Resources: 0 added, 1 changed, 0 destroyed.
```

The guest never re-reads that metadata, so nothing consumes the key and nothing
joins the tailnet — while the apply reports complete success. Use:

```sh
./run rekey            # mint + apply + re-run startup over IAP (no downtime)
./run rekey --reboot    # same, but stop/start instead — needs only the Compute API
```

`rekey` re-triggers the startup script rather than running `tailscale up` by hand,
so the key is read from metadata instead of being passed on a command line. The
default path goes over `gcloud compute ssh --tunnel-through-iap`, deliberately:
if you are running this, Tailscale is broken, so the tailnet is not available as
a transport. It is safe on a healthy box — the startup script only spends a key
when the node is not already a member, so it just re-asserts `--ssh`.

### A dead key fails the apply, not the boot

A spent, expired, or **revoked** key is otherwise invisible until the VM has
booted and silently failed to join — at which point it is unreachable by design
and the failure looks like a hung build. `./run apply` therefore validates the
key against the Tailscale API first (`./run check-key` runs it standalone):

```
ERROR: the Tailscale auth key Terraform is about to use is NOT usable.

  key id : REDACTED
  state  : revoked or spent at 2026-08-03T10:27:56Z
  source : terraform/tailscale.auto.tfvars
```

One-off keys are marked revoked the moment they are *consumed*, so an invalid key
is only fatal when the node still needs it. If the node is already on the tailnet
the spent key is expected and you get a warning instead — an unrelated apply is
never blocked over it.

> Revoking a key in the admin console *after* minting it produces exactly this,
> and the Tailscale audit log will show it
> (`GET /api/v2/tailnet/-/logging/configuration`, `action: REVOKE`,
> `origin: ADMIN_CONSOLE`). Let the tooling manage its own keys.

A rebuilt VM presents a **new SSH host key**. The scripts use
`StrictHostKeyChecking=accept-new`, so an *unknown* host is accepted
automatically, but a *stale* entry from a previous build still (correctly)
refuses to connect. `verify.sh` detects that case by name and tells you to run:

```sh
ssh-keygen -R cloud-agent
```

`provision-phone.sh` and `verify.sh` are both idempotent and safe to re-run.
`provision-phone.sh` only ever removes keys whose comment ends in
`-notify-phone`, validates the new pubkey with `ssh-keygen` before writing, and
rolls `authorized_keys` back if any pre-existing key would be lost — your laptop
key cannot be collateral damage.

**Want to skip the phone step entirely?** Keep the data disk, and the notify
keypair (plus the tailnet node identity and your browser logins) survives:

```sh
./run tf destroy -target=google_compute_instance.agent
./run apply
```

## Setup

### 1. Bootstrap + provision

```sh
./run up
```

From an empty project that does the whole thing: creates the GCS state bucket,
enables versioning, writes `terraform/backend.tf`, runs `terraform init`, mints a
single-use auth key, builds the VM, attaches the data disk, waits while the
startup script mounts the disk / installs Tailscale / creates your user / joins
the tailnet with SSH enabled, provisions the phone, and verifies the result.

To watch it happen step by step instead, the pieces are still there:

```sh
./run bootstrap && ./run plan
./run apply && ./run wait && ./run phone && ./run verify
```

### 2. Connect

The box is reachable ~84s after the instance is created — phase A brings
Tailscale up and stops there. The rest (packages, browser stack, Node, opencode)
installs in the background for another ~4 min; `./run wait --packages` blocks for
it, and `tail -f /var/log/startup-agent.log` over IAP shows phase A. Then from
your laptop:

```sh
ssh youruser@cloud-agent      # tailnet hostname == instance_name
```

Tailscale SSH authenticates via your tailnet identity — no key setup, no port.
You land on the real Debian box as your user.

> If the name doesn't resolve, check `tailscale status` for the node and its
> `100.x` IP, and confirm your tailnet **ACLs** permit SSH (see Gotchas).

### 3. Provision your environment (by hand, first time)

```sh
# on the box
sudo apt update && sudo apt upgrade -y
git clone <your-dotfiles-repo> ~/dotfiles
cd ~/dotfiles && stow */
# install your usual tools with apt
```

Put anything you want to persist across VM rebuilds under `/mnt/data`.

## Browsers: two of them, and the difference matters

Agents get a **real browser** — many sites block or flag `HeadlessChrome`, so the
box runs Chromium *headed* on a virtual display. No desktop or window manager:
**Xvfb** provides a 1920×1080 screen (`DISPLAY :99`) and Chromium renders into it
exactly like a normal browser. `DISPLAY=:99` is pre-set in every login shell and
tmux (via `/etc/profile.d`).

There are two wrappers, and using the wrong one is the one mistake here with a
lasting cost:

| | `headed-chromium` | `social-chromium` |
|---|---|---|
| For | testing **our own** apps | a **real account** that is logged in |
| CDP | yes, `CDP_PORT` (default 9222) | **never** — refuses, exit 64 |
| Profile | `/mnt/data/browser/default` | `/mnt/data/browser/social-<platform>` |
| Control | Playwright / CDP | by hand today; an extension over a local WebSocket once built (`SPEC.md`) |

```sh
headed-chromium https://example.com                     # test browser
BROWSER_PROFILE_DIR=/mnt/data/browser/agent2 CDP_PORT=9223 headed-chromium
./run login                                             # hand-login, over VNC
./run login --verify                                    # still logged in?
```

- Playwright: `chromium.launch(headless=False, executable_path="/usr/bin/chromium")`,
  or attach: `chromium.connect_over_cdp("http://localhost:9222")`.
- Logged-in sessions survive rebuilds (profiles live on the data disk).
- Each headed Chromium costs ~530 MB (measured); a browser sitting on a busy
  feed also costs about a full core, so park it on `about:blank` or stop it.
- `social-chromium` deliberately has no fingerprint-spoofing flags. Coherence
  beats invisibility, and datacenter-IP scoring is not something a flag fixes —
  the reasoning, and why there is no proxy,
  is in [`docs/decisions/browser-and-social.md`](docs/decisions/browser-and-social.md).

### The one-time social login

`./run login [platform]` does the whole thing: starts `x11vnc` on the box
(loopback only), launches `social-chromium` on `:99`, opens an SSH tunnel
`localhost:5900 → box:5900`, and opens your local VNC client. You log in by hand,
including 2FA; on exit the tunnel closes and `x11vnc` stops.

```sh
./run login                     # log in (needs a VNC client locally, e.g. tigervnc)
./run login --verify            # cookie-jar evidence only, sends no traffic
./run login --verify --deep     # ...plus ONE authenticated request
./run login --stop              # SIGTERM the browser, so cookies flush
VNC_LOCAL_PORT=5901 ./run login # if 5900 is taken
SOCIAL_WINDOW_SIZE=1440,900 ./run login   # size it to your screen
```

Exit codes for `--verify`: `0` logged in, `1` not, `2` cannot tell — the last one
is a different problem from the second and should be looked at, not retried.

Do **not** log in on your laptop and copy the cookie over; the reason is in the
decisions doc, and it is not a style preference.

## Phone notifications (Termux)

Agents can ping your phone (e.g. "build finished", "needs your input") via
`notify-phone "<title>" "<message>" [extra flags]`. The VM is the SSH
*client* here — it dials **out** to Termux's own `sshd` on your phone over
the tailnet and runs `termux-notification` remotely. No inbound sshd/firewall
changes on the VM, no port/socket forwarding, no Tailscale SSH involved (it
doesn't support forwarding) — just a plain outbound, key-authenticated SSH
connection.

```sh
notify-phone "Build" "finished on cloud-agent"
notify-phone "Tests" "3 failed — tap to open" \
  --action "android.intent.action.VIEW" \
  --icon-path /sdcard/Download/ic_fail.png
```

Any `termux-notification` flags pass straight through (`--action` takes an
Android intent action; `--icon-path` is a path **on the phone** — run
`termux-setup-storage` once to expose `/sdcard`). The wrapper `%q`-escapes
every argument, so multi-word and special-character text survives ssh's
space-joining intact (ssh does not preserve your quoting). If the phone (or
its tailscale) is down, `notify-phone` **fails fast** (~5s, non-zero exit) —
append `|| true` if notifications are best-effort.

The dedicated ed25519 keypair and `known_hosts` used for this live on the
persistent data disk (`/mnt/data/ssh-termux/`), so a VM rebuild doesn't
require re-adding the key to your phone.

**One-time setup on the phone (Termux), by hand:**

```sh
pkg install openssh termux-api termux-services python
sshd             # starts sshd right now, on port 8022
whoami           # note this — it's TF_VAR_termux_ssh_user
```

Termux is an unprivileged Android app, so it **cannot bind port 22** — `sshd`
listens on **8022** (hence the `TF_VAR_termux_ssh_port` default). There is
also **no password**: Termux accounts have none until you run `passwd`, so
authentication is by key only — see the `authorized_keys` step below.

To keep sshd running:

```sh
# Fully restart Termux first (swipe it from recents) — termux-services'
# runsvdir starts from ~/.profile. Until you do, sv-enable fails with
# "file does not exist".
sv-enable sshd
sv up sshd
```

Also on the phone: install the **Termux:Boot** app and open it once (sshd
won't survive a phone reboot otherwise), **exempt Termux from battery
optimization** (Settings → Apps → Termux → Battery → Unrestricted) or Doze
kills it, and on Android 13+ grant **Termux:API the notification permission**
(the first notification triggers the prompt). `python` is only needed for the
hardening parser below.

Then, after `./run apply`, grab the generated public key from the VM
(`tail -f /var/log/startup-agent.log` on first boot, or
`cat /mnt/data/ssh-termux/id_ed25519.pub`) and append it to
`~/.ssh/authorized_keys` in Termux.

Configure via `TF_VAR_termux_host` (phone's Tailscale MagicDNS name, defaults
to `galaxy-s24-ultra`), `TF_VAR_termux_ssh_port` (Termux sshd default
`8022`), and `TF_VAR_termux_ssh_user` (from `whoami` above — required, since
Termux's sshd checks it even though auth is by key). The feature is only
provisioned when **both** host and user are set (otherwise the startup script
skips it and says so in the log).

### Hardening the phone key (optional, recommended)

By default the key can open a full shell on your phone. To lock it to
notifications only, use a **forced command** on the phone side. The parser is
python's `shlex` — pure parsing, **no shell eval** — so any flags work
(`--action`, `--icon-path`, `--button1`, ...) and any message content (`$`,
`&`, `;`, quotes) is just data. Injection is impossible by construction.

`~/bin/notify-only` in Termux (`chmod +x`):

```python
#!/data/data/com.termux/files/usr/bin/python3
# Forced-command target for the notify-phone key: run ONLY termux-notification,
# with any flags. sshd puts the original command in SSH_ORIGINAL_COMMAND as one
# string; shlex splits it (no eval), so metacharacters in the message are data.
import os, shlex, sys

BIN = "/data/data/com.termux/files/usr/bin/termux-notification"

raw = os.environ.get("SSH_ORIGINAL_COMMAND", "")
try:
    argv = shlex.split(raw)
except ValueError as e:
    sys.exit(f"refused: unbalanced quoting ({e})")
if not argv or argv[0] != "termux-notification":
    sys.exit("refused: this key may only run termux-notification")
os.execv(BIN, argv)
```

and in `~/.ssh/authorized_keys` use this line *instead of* the plain pubkey:

```
restrict,command="$HOME/bin/notify-only" ssh-ed25519 AAAA... sagi@cloud-agent-notify-phone
```

`restrict` additionally disables PTY, port/agent forwarding, X11 and user-rc
for this key. Nothing on the VM side changes — the hardened and unhardened
setups use the same `notify-phone`.

Verified against Termux's OpenSSH 10.4: the restricted key sends notifications
(exit 0) but is refused a shell command or an interactive session, and `$HOME`
expands correctly inside `command=`. Because `shlex` never invokes a shell,
a chaining attempt like `termux-notification -t X -c Y; id` doesn't execute
anything — the `;` is just a character in an argument, so the worst case is
`termux-notification` complaining about too many arguments.

## Teardown

**Full wipe by default** — destroys the VM + data disk, deletes the GCS state
bucket, and removes local Terraform artifacts:

```sh
./run cleanup                # FULL wipe (compute + bucket + files + tailnet node)
./run cleanup --yes          # same, skip confirmation prompts
./scripts/cleanup.sh --keep-bucket   # keep the state bucket
./scripts/cleanup.sh --keep-files    # keep local .terraform / backend.tf / state
```

Each destructive step prompts unless `--yes` is passed. Re-provision afterward
with `./run up`.

> **`cleanup` is not "reset".** Answering `y` to all three prompts deletes the
> data disk — everything under `/mnt/data`, the tailnet node identity, and the
> notify keypair — plus the state bucket, which is the only record of what exists.
> There is no undo, and versioning does not save you because the bucket itself is
> removed. If your goal is "make it work again", that is `./run up`; if it is
> "throw the VM away but keep my data", that is:
>
> ```sh
> ./run tf destroy -target=google_compute_instance.agent && ./run up
> ```

## Security: no public inbound

The VM runs on its **own dedicated VPC** (`network.tf`), not GCP's `default`
network — to avoid the auto-created permissive rules (`default-allow-ssh`,
`-rdp`, `-icmp`) that open tcp:22, tcp:3389, and icmp to `0.0.0.0/0`.

The firewall allows only:

- **Ingress tcp:22 from `35.235.240.0/20`** — Google's IAP range, so
  `gcloud compute ssh --tunnel-through-iap` works as a break-glass path.
- **Ingress within the subnet** (`10.10.0.0/24`).
- **All egress** — Tailscale dials out; apt/git need the internet.

There is **no public inbound** for your actual access — you reach the box over
the **Tailscale tailnet**, established outbound, needing zero inbound rules.
Nothing on the public internet can reach the VM.

Your user has **passwordless sudo** on the box. That's acceptable here because
the only ways in are your tailnet identity (Tailscale SSH) and your Google
identity (IAP), both enforced off-box — and a passworded sudo could never work
anyway (`useradd` creates the account password-locked, so no password would
ever match).

### If you still have GCP's default rules

```sh
gcloud compute firewall-rules list \
  --format="table(name,network,sourceRanges.list())"
# delete the internet-facing ones (keep default-allow-internal):
gcloud compute firewall-rules delete default-allow-ssh default-allow-rdp default-allow-icmp --quiet
```

## Gotchas (learned the hard way)

- **GCP's `default` network is wide open** (tcp:22, 3389, icmp from
  `0.0.0.0/0`). Use the dedicated VPC in `network.tf`, or delete those rules.
- **Deleting `default-allow-ssh` makes plain `gcloud compute ssh` hang** — it
  has no route in. Use `--tunnel-through-iap` (needs the IAP-range rule), or
  rely on Tailscale.
- **Tailscale SSH needs an ACL** granting it. In the tailnet admin console add
  an `ssh` rule (e.g. `action: accept`, `src: autogroup:member`,
  `dst: autogroup:self`, `users: [youruser, autogroup:nonroot]`).
- **`tailscale up` won't silently drop a flag.** To change settings toward
  defaults, use `--reset`.
- **`terraform apply` cannot deliver a new auth key to a running VM.** The key
  travels in `startup-script` metadata, and GCE only runs that at boot, so the
  apply reports `1 changed` / `Apply complete!` while the guest never reads it and
  the key is never consumed. Use `./run rekey`.
- **Don't revoke an auth key in the admin console mid-build.** A key revoked
  between `mint` and `apply` gets baked into the VM, `tailscale up` fails with
  `invalid key: API key <id> not valid`, and the box is then unreachable by design
  — the symptom is a 5-minute `wait-ready` timeout that reads like an
  infrastructure fault. `./run apply` now validates the key against the API first,
  and the Tailscale audit log
  (`GET /api/v2/tailnet/-/logging/configuration`) attributes every `REVOKE`.
- **Terraform's variable precedence puts `*.auto.tfvars` above `TF_VAR_*` env
  vars.** So a `TF_VAR_tailscale_auth_key` in `config.env` is silently ignored
  while `tailscale.auto.tfvars` exists, then silently takes effect (as a
  long-spent key) if that file ever goes missing. Set one or the other.
- **Use `findmnt`, not `ls`,** to verify a mount — an empty dir and a mounted
  dir look identical to `ls`.
- **`blkid` before `mkfs`.** Don't reformat a disk that already has a
  filesystem (the startup script guards this).
- **Don't symlink `/var/lib/tailscale`.** The distro `tailscaled.service`
  sets `StateDirectory=tailscale`, and systemd refuses to enter a symlinked
  state dir (status 238, "Too many levels of symbolic links"). Bind-mount
  the persistent dir over it instead (the startup script does).
- **Billing must be enabled** or `gcloud services enable` fails before
  Terraform runs.
- **Key injection on first boot can lag** on a fresh VM; give it a minute.
  Tailscale is your primary access anyway.
- **In an HCL heredoc, `$$` is an escape only before `{`.** `$${VAR}` yields
  `${VAR}`, but `$$VAR`/`$$@` render as two literal dollars, which bash then
  expands to the **PID**. This silently corrupted both `notify-phone` (the phone
  refused the mangled command) and `headed-chromium` (it dropped every argument
  and passed `<pid>@`). Write bare `$VAR`, `$@`, `$?`. A `lifecycle precondition`
  in `compute.tf` now fails the apply if any `$$` survives rendering — and always
  verify against the *rendered* script (`gcloud compute instances describe`),
  never against a hand-rolled unescape, which is how this hid in the first place.
- **`ssh host cmd arg1 arg2` joins argv with spaces and the remote shell
  re-parses it.** Quoting is *not* preserved, so multi-word values arrive split
  and quotes get stripped. `notify-phone` solves this with `printf %q` per
  argument plus `shlex.split` on the phone; `provision-phone.sh` embeds its value
  as a `%q`-escaped assignment instead of passing it as an argument.
- **`ssh` eats stdin.** Piping a script to `bash -s` over ssh and then calling
  `ssh` (or `notify-phone`) inside it makes the inner ssh consume the rest of the
  script, silently truncating it. Use `ssh -n` or `</dev/null`; `notify-phone`
  passes `-n` for exactly this reason.
- **Non-interactive ssh has a minimal PATH.** `swapon`/`zramctl` live in
  `/usr/sbin`, so `ssh host swapon --show` fails with "command not found" and
  looks like the feature is broken rather than missing from PATH.
- **`DEBIAN_FRONTEND=noninteractive` does NOT stop dpkg conffile prompts.** It
  governs debconf. If a package ships a config file that already exists on disk,
  dpkg stops and asks on stdin — and in a startup script there is no stdin, so it
  dies with `end of file on stdin at conffile prompt` and apt exits 100. Always
  pass `-o Dpkg::Options::=--force-confold`.
- **A conffile conflict poisons the box permanently, not just once.** The failed
  package is left half-configured (dpkg state `iU`), so every *later*
  `apt-get install` tries to configure it again and fails identically. With
  `set -e` that aborts the startup script early — before `tailscale up` — so the
  VM stops being reachable *and* stops being able to re-key itself, on every
  subsequent boot. Repair with `dpkg --configure --force-confold -a`.
- **Never pre-create a file that a package owns as a conffile.** Writing
  `/etc/default/zramswap` before installing `zram-tools` caused exactly the two
  bugs above. Install first, configure second.
- **The last line of a startup script may never reach the serial console.** With
  `exec > >(tee ...)`, bash does not wait for `tee` to flush its stdout into the
  metadata runner's pipe before exiting, so the final line lands in the on-disk
  log but can be dropped from the journal. `wait-ready.sh` polled the console for
  exactly that marker, so a healthy 84-second boot presented as a 10-minute
  timeout. Milestones now also go through `logger` (synchronous, journal) and a
  sentinel file at `/run/agent-startup-complete` that is checked over SSH.
- **gcloud `--filter` can be pushed SERVER-side and rejected.**
  `--filter='direction=INGRESS AND sourceRanges~0.0.0.0/0 AND disabled=false'`
  becomes an API filter GCP refuses (`Invalid list filter expression`), so the
  command errors and prints nothing — identical to "no open rules". That made the
  most important security assertion in `verify.sh` a permanent silent PASS that
  had never once actually run. It now lists plainly and matches client-side.
- **gcloud and Terraform authenticate SEPARATELY.** Terraform uses
  application-default credentials; the `gcloud` CLI uses its own active account.
  They drift apart the moment you `gcloud config set account` or log a second
  identity in, and the result is baffling: `terraform apply` builds the VM happily
  while every `gcloud`-based check insists the instance does not exist. `gcloud
  auth list` and `gcloud config list` are the diagnosis; `instance_status` now
  reports `unknown` rather than `absent` so nothing mistakes it for a deleted VM.
- **Don't let a failed API call read as a passing check.** `gcloud compute
  firewall-rules list` prints nothing both when there are no open rules and when
  it has no permission — so the "no public ingress" assertion silently PASSed on
  error until it started checking the exit code. A security check that cannot run
  must FAIL, never pass.
- **Anything slow in the foreground of `startup-script` is time the box is
  unreachable.** There is no public inbound until `tailscale up`, so a five-minute
  package install is five minutes of a VM that cannot be reached or debugged, and
  five minutes before a bad auth key even surfaces. Keep phase A minimal; defer
  the rest to `agent-packages.service`.
- **Do not write a literal doubled dollar inside the `startup.tf` heredoc** — not
  even in a comment. HCL passes it straight through and the `compute.tf`
  precondition then rejects the apply. (It caught exactly that in a comment I
  added about the doubled-dollar guards.)
- **`cleanup` is a wipe, not a reset.** Three `y` answers destroy the data disk
  (all of `/mnt/data`, the tailnet node identity, the notify keypair) and the
  state bucket. Nothing is recoverable afterwards — bucket versioning cannot help,
  because the bucket is deleted too. To fix a broken box use `./run up`, which is
  non-destructive; to replace just the VM, `tf destroy -target=...instance.agent`.
- **Never delete the state bucket or `backend.tf` while resources exist.** They
  are the only pointers to live infrastructure, and `cleanup.sh` skips the
  destroy entirely when `backend.tf` is absent — so the VM keeps billing with
  nothing tracking it. `cleanup.sh` now verifies with `gcloud` that the instance
  and disk are really gone before either wipe, and refuses otherwise
  (`--force` overrides).

## Persistence model

- **Disposable:** the VM and its root disk. Rebuild freely.
- **Persistent:** the separate data disk at `/mnt/data` — put repos, work
  output, and anything you can't lose here. Tailscale state is bind-mounted
  here too (`/var/lib/tailscale` → `/mnt/data/tailscale`), so a rebuild keeps
  the   node identity (no re-auth) as long as the data disk survives. Browser
  profiles (`/mnt/data/browser/`) live here as well — logins survive too.
- A full `cleanup.sh` deletes the data disk too. Use `--keep-*` flags or
  snapshot the disk first if you want to preserve it.

## Measuring the box

Sizing decisions in this repo come from measurement, not opinion, and the tools
are checked in so a claim can be re-checked:

```sh
./run measure --seconds 120 --label "two agents"   # PSS by user and kind, peaks
./run lsp-probe --cmd "tsgo --lsp --stdio" --root /mnt/data/repos/ts --quiet 30
```

`measure` reports **PSS**, not RSS, because per-client isolation means several
copies of the same binaries sharing pages, and RSS overestimates in the direction
that costs money. Results and their caveats:
[`docs/measurements.md`](docs/measurements.md).

Open ideas, not yet decided: bake dotfiles into the startup script, snapshot the
data disk on a schedule, pin `debian-12` to a dated image for bit-reproducible
rebuilds (the family tracks Google's latest).
